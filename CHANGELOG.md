# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Add new entries under `[Unreleased]` in the same commit as the code change.

## [Unreleased]

### Changed

- The shared source monitoring interface names its selection `status_ids` rather than RV-C-specific `dgns`; RV-C continues interpreting those identifiers as DGNs, while WLED reads a whole-controller snapshot.
- The local `rv-control-web` controller policy now grants all eight `patio_strip` WLED actions, adding `color`, `effect`, `palette`, `transition`, and `preset` while retaining overlay-defined parameter validation.
- The factory Thor Magnitude BH35 2020 definition no longer includes a WLED template. The local `coach-overlay.yml` and shareable WLED overlay example now own the complete `wled_light` template and custom lights, preserving on/off/brightness and advanced actions when `[coach] overlay` is configured.

### Fixed

- WLED coach entities now receive actual polled brightness and power state, including changes made outside the dashboard, through `<base_topic>/coach/entity/<entity>`. The WLED overlay example maps `on`, raw `bri` and percent `level`; existing local templates must add its `state` block. Temporary HTTP failures retry at the next `poll_interval`, and safe `refresh_states` queries now read WLED state. Coach state blocks without `dgn` consume the bound source's telemetry topic for any source (optional `topic_suffix` for subtopics); BLE polling/notification schedules and write gates are unchanged.
- Coach MQTT startup errors now identify unknown controller-policy targets and point to `[coach] specfile` / `overlay` or stale action grants, making missing installation overlays diagnosable without weakening policy validation.

### Added

- Opt-in `rvcontrol --reload-config run` watches the selected INI (default disabled), requiring both a changed modification timestamp and changed bytes. Validated edits gracefully restart sources, targets, coach services and runtime bindings; invalid/missing files leave the active session running, and timestamp-only touches do not restart. Referenced YAML/policy files are not watched independently.
- Shared runtime constants (`constants` JSON in `[variables]` / `[variables.NAME]`) and restricted arithmetic in `[derived]` / `[derived.NAME]`, with startup dependency/cycle validation and inherited input freshness. All source telemetry uses the same binding engine; Open-Meteo now receives resolved settings through shared source-base polling/wait/retry handling without interpreting variable syntax. Existing hardware connection settings and write gates are unchanged.
- Opt-in `[runtime] publish_variables`, configurable `variables_topic` (default `variables`) and `variables_republish_seconds` (default 60, 0 disables repeats) publish namespace snapshots through existing targets, including `<base_topic>/variables/<namespace>` on MQTT. Snapshots include per-variable availability, null unavailable values and original UTC measurement/expiry metadata; a timer announces expiry without incoming telemetry. Publication is disabled by default and does not restore stale retained inputs.
- Optional Open-Meteo `daily` variable selection adds a seven-day forecast in the existing `<base_topic>/weather` JSON payload, using the location's timezone and preserving daily units and timezone metadata. The configuration example now requests expanded current conditions plus daily highs/lows, sunrise/sunset, precipitation, wind, and UV for dashboards. Omitted or blank `daily` preserves current-only behavior; existing installations must update their weather selections to enable the expanded data.
- `open_meteo` source publishes current weather to `<base_topic>/weather` using literal `latitude` / `longitude` or Bash-style runtime references such as `${location.latitude}`. `[variables.location]` binds `topic`, `fields`, optional `require`, and `max_age` to fresh telemetry without coupling sources; invalid/incomplete reports invalidate whole groups. `check` and daemon startup reject unknown references, unavailable producers, and dependency cycles. Weather uses `poll_interval`, `timeout`, `retry_delay`, `max_retry_delay`, and `current`, waits for valid coordinates, and never sends requests for stale inputs. The example enables `gpsd, weather` in `[source] enabled-sources`; remove `weather` to disable sending coordinates to Open-Meteo. Existing local configurations are unchanged.
- `tools/bt_discovery.py` retains its default Renogy/Hughes scan and adds `--all`, advertisement details/JSON export, explicit `inspect` GATT inventory, selected-characteristic `read`, and bounded `listen` JSONL notification capture. Operations use the selected adapter, report failures, clean up connections, and never overwrite evidence files; no arbitrary application writes or explicit pairing are added. `docs/BLE-DISCOVERY.md` provides a human/AI-agent job aid for investigating unknown BLE devices without assuming protocol compatibility.
- Discoverable writable-source action contracts for RV-C and WLED, inspectable without hardware through `rvcontrol source-actions rvc` / `wled`. Coach translates existing YAML into validated source-owned actions while preserving entity action names, MQTT topics, controller grants, frame ordering and write gates; no YAML or configuration-key migration is required. Recognized local WLED recipes now also enforce source parameter types/ranges. RV-C/WLED encoding and dispatch planning budgets belong to their sources.
- Optional `[coach] overlay` loads additive installation YAML after the factory coach file, with relative paths resolved beside the INI. Conflicting or inherited overrides, invalid state/schema definitions and cyclic/unknown group references fail before hardware access. Factory safety reservations remain in force. A shareable `wled-overlay-example.yml` adds advanced WLED actions without modifying factory definitions; local `coach-overlay.yml` files are Git-ignored.
- Custom patio WLED entity `patio_light` and its dependent `evening_scene` now live in the installation overlay and shareable WLED overlay example, not the factory Thor definition. Factory-only configurations no longer expose these customization targets; example MQTT grants are optional and require the overlay.
- WLED effect and palette discovery through `WledSource.effects()` / `palettes()` and `tools/wled_tool.py effects` / `palettes`, returning controller-ordered JSON name arrays without write enablement. The optional WLED overlay adds segment RGB `color`, `effect`, `palette`, controller `transition` (100 ms units), and saved `preset` selection with typed MQTT parameter schemas and optional example controller grants. Existing polling topics and write gates are unchanged; no awning power sequencing or boot-wait behavior is added.
- Opt-in semantic MQTT coach commands and monitoring on `<base_topic>/coach/command` and `<base_topic>/coach/query`, with correlated QoS-1 non-retained results on `<base_topic>/coach/result/<client_id>/<request_id>`. `[coach_commands] enabled`, `queries_enabled`, `controllers_file`, `journal_file`, and `journal_max_entries` configure independent write/read endpoints, explicit controller grants and durable duplicate/crash protection. Full-group preflight, typed `action_schemas`, confirmation, expiry, bounded single-worker admission, source write gates and reliable transport failure reporting protect physical commands. Monitoring includes timestamp-preserving snapshots/republishing, mapped status refresh, capabilities, health and request-result lookup.
- `rvcontrol mqtt-command ENTITY ACTION` and `rvcontrol mqtt-query ACTION` (also `tools/coach_mqtt.py`) submit correlated requests through the configured MQTT broker without direct hardware access. Supports typed parameters, confirmation, selected-entity refresh and JSON results; timed-out physical requests are never automatically retried. See `docs/COACH-MQTT-COMMANDS.md` and `config-example-controllers.yaml` for setup.
- Coach entity state over MQTT: when `config.ini` has a `[coach]` section, `rvcontrol run` publishes each entity's live state (for example `on`, `level`, tank `level` percent, generator `status`, A/C `mode` and `ambient_c`) as JSON to `<base_topic>/coach/entity/<entity>` (default `rv/coach/entity/<entity>`), built from the coach file's `state` blocks. State is published on change and republished unchanged every `[coach] state_republish_seconds` (default 60, 0 disables); `[coach] publish_state = false` turns it off. At startup the daemon broadcasts one RV-C status Request per tracked DGN so lights and fans that are off are reported without being toggled; `[coach] request_status_on_start = false` disables it. State field specs support `invalid`, `divide_by`, `scale`, `offset`, `round` and `map`.
- Coach entities: coach files describe named devices under `entities`, built from reusable `templates`, with multi-frame actions (optional per-frame `wait`), raw-payload or named DC dimmer frames, runtime `{parameter}` placeholders, `reserved` instances that are never controlled, and `confirm: true` entities. `rvcontrol coach-exec <entity> <action>` runs them; the new `--confirm` flag is required for confirm entities; `coach-list` reports `entities`. Command groups may list `members` with shared action names.
- Thor Magnitude BH35 coach file maps every RV-C entity identified on the bus: 13 lights, 3 roof fans, the kitchen fan lid, awning, water pump, tank heat, generator, front/rear A/C, the LPG furnace, and 5 tanks, plus the patio WLED strip and groups `all_interior_lights`, `all_exterior_lights`, `all_fans` and `evening_scene`.
- `tools/rvc_monitor.py server -v` / `--verbose` echoes the raw bytes sent (`TX`) and received (`RX`) on the client socket, including the handshake and streamed JSON frames, to local stderr with the auth token redacted.
- `[service] log_level` in `config.ini` controls the default logging threshold (DEBUG, INFO, WARNING, ERROR, or CRITICAL); `--verbose` continues to override it with DEBUG.
- `tools/obd_tool.py server -v` / `--verbose` echoes forwarded requests, raw responses, and command errors to local stderr without echoing authentication exchanges or changing the TCP client stream.
- `tools/rvc_monitor.py server` streams raw CAN fields and decoded RV-C messages over receive-only authenticated TCP, with configurable `--host`, `--port` (default `35001`), `--auth-token` / `RVC_SERVER_AUTH_TOKEN`, and `--write-timeout`. Includes a remote Kiro debug runbook; existing local monitoring remains the default.
- `tools/obd_tool.py server` offers a temporary, single-client plain TCP ELM327 debug bridge with generated-token authentication, configurable `--host`, `--port`, `--auth-token` / `OBD_SERVER_AUTH_TOKEN`, and `--idle-timeout`. It is read-only by default; `--allow-unsafe` explicitly enables unrestricted AT/hex passthrough, including possible ECU writes.
- `tools/obd_tool.py check-pids --output FILE` saves the completed PID report as JSON while retaining terminal output; existing reports are replaced atomically and file errors are reported.
- `tools/obd_tool.py check-pids` checks all configured OBD PIDs once, including manufacturer-specific requests and per-PID ECU headers, and reports usable values, individual errors, summary counts, and elapsed time without MQTT publishing.
- Pluggable telemetry targets: `Target` ABC ([src/rv_control/target.py](src/rv_control/target.py)) with a self-registering registry, mirroring `Source`. Targets are enabled via `[target] enabled-targets` (section names, each with a `type`); several targets fan out through `MultiTarget`, where one target's failure does not affect the others.
- `store` target ([src/rv_control/store.py](src/rv_control/store.py)) that keeps the latest payload per full topic (e.g. `rv/renogy`) in a local JSON file (`directory`, `filename`, `flush_interval`; default `data/state.json`), written atomically from a background thread.
- `log` target ([src/rv_control/log.py](src/rv_control/log.py)) that logs each full topic and JSON payload at a configurable `level` without storing or forwarding anything, for debugging sources.
- `[target]`, `[store]`, and `[log]` sections in `config-example.ini`, README "Targets" documentation, and `tests/test_target.py`.
- ELM327 Bluetooth OBD-II source (`type = obd`, [src/rv_control/obd.py](src/rv_control/obd.py)) that polls configured PIDs read-only over a raw Bluetooth RFCOMM socket (no `rfcomm bind`, no `pyserial`) and publishes them to MQTT.
  - PIDs are configured in the source's INI section as `pid.<name> = mode, pid, decode, unit`; decode expressions over `b0`, `b1`, … are validated against a safe arithmetic subset and compiled once at startup.
  - Only read-only OBD modes (01, 02, 03, 05, 06, 07, 09, 0A, 21, 22) are accepted; the source does not accept MQTT commands.
  - Adapter initialization (`ATZ`, `ATE0`, `ATL0`, `ATS0`, `ATH0`, `ATSP<protocol>`, `ATSH<header>`), ECU probe with `0100`, and optional `fallback_protocol` when automatic detection fails.
  - Responses are read until the ELM327 `>` prompt; `SEARCHING...`, multi-frame (`0:`/`1:`) and multi-ECU replies, error strings, and negative responses are handled, and the echoed mode/PID is verified before decoding.
  - Per-cycle flat snapshots on `<base_topic>/<topic>` (failed PIDs are `null`) and availability changes on `<base_topic>/<topic>/status` with adapter version, battery voltage, and protocol.
  - When the source goes offline (engine off or adapter lost), an all-`null` snapshot is published to `<base_topic>/<topic>` so snapshot-only consumers such as rv-control-ui clear stale engine values.
  - Engine on/off resilience: an unreachable adapter or a silent ECU (`max_failed_cycles`) is treated as offline, the socket is closed, and reconnects use exponential backoff (`reconnect_delay`, `max_reconnect_delay`, `max_retry`, inheriting `[service]` when blank). State transitions are logged once.
  - Fixed-rate polling at `poll_hz` with a one-time warning when a cycle overruns.
  - `adapter` selects the local Bluetooth controller by `hciN` name or controller MAC, and the RFCOMM socket is bound to it.
  - `comms-check` passes when the adapter answers (even with the engine off) and lists configured PIDs and units; `interrogate` returns one reading of every PID.
- `tools/obd_tool.py` with `info`, `supported`, `read`, `monitor`, and `query` commands for direct, read-only adapter access using the same INI section.
- `[obd_engine]` example section in `config-example.ini`.
- Expanded the example OBD-II PID set with the requested Power Stroke towing signals while retaining the existing EGT11, RPM, and coolant-temperature entries; transmission PIDs can specify their `7E1` CAN header, and Boost uses the configured Baro reading.
- Synchronous `connect_slot_sync()` on the Bluetooth adapter coordinator so RFCOMM connects serialize with BLE connection setup on a shared adapter.
- README documentation for the OBD source and a Raspberry Pi guide for ELM327 adapter selection, controller selection, discovery, pairing, RFCOMM channel lookup, permissions, and troubleshooting.
- `tests/test_obd.py` covering PID parsing, decode safety, response parsing, adapter I/O, interrogation, fallback protocol, comms-check, daemon reconnects, retry limits, and adapter resolution.
- This changelog, and a steering rule requiring changelog updates with code commits.

### Changed

- Renogy daemon operation always polls every `poll_interval` seconds. With `persistent_connection = false` it connects, reads all registers, and disconnects each cycle so the device stays available to the Renogy phone app between polls; `persistent_connection = true` (or blank with `daemon_mode = true`) keeps the link open as before. Previously, non-persistent daemon operation without `enable_polling` reconnected about once per second.

- CLI logs now include the source filename, line number, and function, including messages emitted through the root logger. Renogy BLE connection failures also identify the device alias, address, and Bluetooth adapter.
- The OBD example comments out `pid.egt11`, `pid.eot`, `pid.boost`, `pid.vgt`, `pid.fipw`, `pid.icp`, and `pid.iat2` after repeated request-out-of-range responses on the tested 2019 F-550. It also disables the mislabeled `pid.app` monitor-status request; definitions remain available for reference.
- The OBD example now explicitly sets `max_retry = 0` to keep retrying while the engine or Bluetooth adapter is unavailable, independently of the `[service]` retry limit.
- Hughes daemon reconnects now log expected Bluetooth unavailability (device not found, BLE errors, timeouts) as a one-line warning with the retry delay instead of a full traceback; unexpected errors still log a traceback.
- `tools/obd_tool.py check-pids` now saves adapter/protocol details, a standard RPM control check, and per-PID response, header, timing, failure-stage, and negative-response-code evidence to distinguish ECU rejection from transport or decoding failures in one report.
- Source tree reorganized: sources (including `renogybt/`) now live in `src/rv_control/sources/` with the `Source` ABC in `sources/base.py`, and targets live in `src/rv_control/targets/` with the `Target` ABC in `targets/base.py`. Shared `bluetooth.py` and `rvc_util.py` stay at the package top level. Python import paths changed (e.g. `rv_control.sources.rvc`, `rv_control.targets.mqtt`); the CLI and configuration contract is unchanged.
- MQTT publishing is now `MqttTarget` ([src/rv_control/mqtt.py](src/rv_control/mqtt.py)), with unchanged topics, payloads, and write gating; `MqttPublisher` remains as an alias. `run` builds publishers with `Target.build`, and command routing locates the MQTT section by `type`.
- `[mqtt]` is no longer required when a `[target]` section is present. Without `[target]`, the legacy `[service] targets` list (default `mqtt`) applies, so existing configs behave as before.
- Configuration files are read as UTF-8 so unit strings such as `°F` load consistently.

### Fixed

- Renogy and Hughes BLE devices no longer become unreachable (to rv-control and the phone app) until power cycled after a dropped or failed connection. Before each connection attempt and after each session, rv-control now asks BlueZ to release any link it still holds to the configured device, and failed Renogy setup always disconnects its client.
- Renogy reconnects no longer leave the previous polling loop running, which stacked overlapping register reads and read timeouts after each drop.
- A Hughes `stop_notify` failure on an already-dropped link no longer masks the original session error.
- OBD ECU probe failures are logged as warnings, and `fallback_protocol` is only tried when the configured protocol is automatic (`0`), preventing a fixed protocol from being retried as its own fallback.
- Renogy BLE connection setup no longer treats transient disconnect callbacks as separate failures or logs each disconnect twice. Retries are serialized and continue through repeated setup failures until recovery or the configured `max_retry` limit, and connection errors now identify the exception instead of printing a traceback-object tuple.
- Corrected and re-enabled `pid.load` in the OBD example: mode 01 PID 04 now decodes calculated engine load as `b0*100/255` (0-100%) without the incorrect negative offset.
- Renogy worker restarts and one-shot interrogation now close their event loops, cancel pending work, and disconnect BLE clients, preventing file-descriptor accumulation and eventual `Too many open files` failures. Shutdown after a failed startup no longer attempts to create another event loop.
- OBD unlimited reconnects no longer stop with a backoff overflow during prolonged `Host is down` or engine-off outages. Retry waits stay capped at `max_reconnect_delay`, reset after ECU recovery, and remain interruptible on shutdown. Invalid non-positive or non-finite retry delays and negative `max_retry` values are rejected before connecting.

### Removed

- Coach `commands` section and its single-frame executor; coach files now use `entities`. The Thor placeholder commands `livingroom_lights`, `bedroom_lights` and `patio_lights` are replaced by `living_ceiling_light`, `bedroom_ceiling_light` and `patio_light`.
